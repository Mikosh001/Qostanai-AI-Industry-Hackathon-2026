# Серверный запуск и проверяемые отчёты

Moodle подписывает запуск Ed25519. Приватный seed хранится только в настройках плагина на сервере Moodle; агент получает открытый ключ проверки. Общий секрет Moodle используется только между сервером Moodle и центральным хабом. Установка этого секрета на агент через API запрещена.

## Подключение администратора

1. Запустите центральный backend с `SERGEK_SERVICE_ROLE=hub`, постоянным `SERGEK_DATA`, HTTPS-сертификатом и доверенным CA. Первую настройку выполните локально через desktop. Не выставляйте bootstrap-ключ в публичный доступ.
2. Создайте отдельный серверный секрет Moodle (32–256 символов) и случайный 32-байтовый Ed25519 seed. Seed задаётся в Moodle, публичный ключ и серверный секрет — на хабе. Для генерации используйте криптографический генератор, например `Ed25519PrivateKey.generate()`, а не пароль человека. Moodle требует расширение PHP sodium.
3. В панели хаба откройте «Интеграция» → «Зарегистрировать компьютер». Полученные `device_id` и `device_key` передайте только этому агенту. Ключ показывается при регистрации один раз; список устройств его не возвращает. На агенте задайте HTTPS-адрес хаба, ID, секрет устройства и публичный ключ Moodle.
4. Включите Require Sergek Proctor в тесте. Разрешите нужные домены LMS/SSO и настройте доверие TLS. Moodle запускается из приложения; оно добавляет непубличный по назначению, но не секретный ID устройства в HTTP-заголовок только для настроенного origin Moodle.
5. При потере компьютера отзовите устройство в панели хаба и зарегистрируйте новое. Отзыв запрещает новые пакеты/lease и немедленно делает Moodle status неактивным; агент узнаёт об отзыве при очередном lease. Приватные ключи Moodle не передаются на компьютеры аудитории.

## Жизненный цикл

`Moodle login → quiz → серверный SG2 launch → зарегистрированный device → preflight → Start attempt → active → attempt_submitted → stop → completed`.

Запуск содержит audience, nonce, пользователя, тест, устройство, разрешённый URL, режим, время выдачи и срок 30 минут. Moodle сначала регистрирует подпись на хабе. Хаб связывает выданный nonce с одним устройством и одной сессией; чужие user/quiz/device, изменённые claims и невыданные запуски отклоняются. Просроченный запуск не создаёт новую сессию. Уже связанная сессия может продолжать синхронизацию после срока запуска.

Каждый агент имеет собственный транспортный HMAC-ключ. Lease обновляется отдельно от загрузки доказательств раз в 2 секунды; данные старше 15 секунд не дают Moodle активный доступ. Пакеты ограничены по размеру, времени и уникальному packet ID. Неправильные Origin/URL, идентификаторы, цепочки и вложения не принимаются. Старый общий pairing key не может создать активную Moodle-сессию.

Moodle хранит связь nonce с реальным attempt ID. Серверный observer уведомляет хаб об отправке. При потерянном callback хаб ограниченным отдельным пулом опрашивает Moodle status.php; сетевую ошибку он не считает завершением. Это резервный путь, его задержка зависит от размера класса и доступности Moodle.

## Доказательства

Агент передаёт события от подтверждённого cursor, без повторной передачи всего журнала. Первая фотография неизменна в пределах сессии и после подтверждения повторно не загружается. Для нового видеоархива нужен SHA-256 commitment внутри цепочки. ZIP проверяется до распаковки: пути, ссылки кадров, времена, число файлов и объём ограничены. Архивы хранятся в AES-GCM; секреты и ключи на Windows защищены DPAPI.

Локальный anchor обнаруживает удаление хвоста, серверный anchor сохраняет уже принятый prefix. Старые сессии без исходного anchor помечаются legacy; им не приписывается доказанная полнота задним числом. Ошибки записи явно отмечают неполноту доказательств и не превращаются в «чистый» отчёт.

Шифрование и staging больших медиа выполняются вне общего DB lock. Одновременно принимаются не более четырёх больших загрузок; маленькие контрольные пакеты проходят отдельно. При нехватке свободного места (reserve по умолчанию 1 ГБ, `SERGEK_DISK_RESERVE_BYTES`) сервер возвращает HTTP 507 и явно отмечает неполноту. Агент отдельно отправляет terminal/control metadata, сохраняя локальные клипы для повторной передачи. Успешный control ack не означает, что все медиа уже доставлены.

JSON-отчёт можно подписать Ed25519. Получите `report_public_key` у администратора центрального хаба независимым каналом, затем:

```powershell
python scripts/Verify-Report.py report.signed.json --public-key TRUSTED_PUBLIC_KEY_HEX
```

Ключ внутри скачанного JSON сам по себе не устанавливает доверие. Подпись доказывает неизменность payload относительно доверенного ключа, а не правдивость каждого AI-наблюдения. Рекомендуется экспортировать итоговые отчёты с центрального хаба; у локального агента отдельный ключ.

## Границы доверия и восстановления

Персональный device key идентифицирует зарегистрированное приложение, но не даёт аппаратную аттестацию Windows. Администратор ОС, украденный device key, модифицированная ОС, виртуальная камера и качественный deepfake требуют отдельного периметра. Управляемые университетские компьютеры, ограниченные права студента, контроль установки и физическая приёмка остаются необходимыми. Полного превосходства над OES/SEB эти изменения не доказывают.

Для резервной копии остановите хаб и сохраните целиком `SERGEK_DATA` с базой, ключами и доказательствами в защищённом хранилище. Секреты DPAPI привязаны к учётной записи Windows: перенос одной базы на другой компьютер не является восстановлением ключей. Проверьте восстановление на отдельном профиле до пилота. Installer пока не имеет Authenticode-подписи; цифровая подпись отчёта не заменяет подпись installer.

## Қазақша қысқаша

Moodle іске қосуды Ed25519 арқылы қолтаңбалайды. Құпия сервер кілті студент компьютеріне берілмейді. Хаб әр компьютерге бөлек кілт береді және оның рұқсатын тоқтата алады. Рұқсат нақты студентке, тестке, компьютерге және бір сессияға байланады. Қорғаныс Moodle-дегі Start attempt басылғанда басталады; басталу/аяқталу UTC уақыты сақталады.

Журнал өсіммен синхрондалады, lease бейне жүктеуден бөлек жаңарады. Anchor журналдың сақталған бөлігін және құйрығының жоғалуын тексереді. Жаңа бейнеүзінді хэші журналға енгізіледі, есепке цифрлық қолтаңба қоюға болады. Тексеру үшін сенімді ашық кілтті университет әкімшісінен бөлек алу қажет. AI оқиғасын мұғалім дәлелімен қарайды; автоматты кінә тағылмайды. Нақты телефон, USB, RDP, Windows қалпына келуі және университет желісі бөлек қабылдау сынағын қажет етеді.
